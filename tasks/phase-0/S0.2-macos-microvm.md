# Spike S0.2 — macOS microVM: boot, virtiofs, identical in-guest capture

**Phase:** 0 · **Kill-risk rank:** 2 · **Owner:** —
**Kills:** *Is the macOS path real — including running agents, not just booting?* If we can't boot a Linux guest via Apple Virtualization from Go, project host dirs over virtiofs, run the S0.1 capture unchanged inside it, stream events to the host over vsock, **and actually run a real Node-based agent in-guest against projected dirs** — then macOS support (where the OpenClaw users are, and where Jay is) is not deliverable as designed, and D2/D15 must change. (v1.1: the runtime question is now explicitly part of the kill criterion — a guest that boots but can't run OpenClaw kills the mac story just as dead.)

## Setup
- Apple Silicon Mac, macOS ≥ 13 (test ≥ 14 for save/restore separately).
- Go + CGO; Code-Hex/vz/v3.
- A minimal Linux kernel + initramfs with BTF, virtiofs, overlayfs (hand-built or off-the-shelf for the spike; Buildroot comes in Phase 3).
- The S0.1 program set, cross-built for the guest arch.

## Steps
1. Boot the guest from Go via vz: kernel + initramfs, serial console to stdout.
2. Attach one `VZVirtioFileSystemDeviceConfiguration` tag for a host test dir; mount it **read-write at `/mnt/host/test`** in-guest (NOT as rootfs — avoid the known virtiofs uid/gid rootfs breakage).
3. Attach a **persistent host-file-backed ext4 data volume**; install Node.js LTS onto it (hand-placed for the spike; the reproducible runtime layer comes in Phase 3).
4. Establish a vsock channel; get a `net.Conn` on the host side. Stand up a minimal **vsock↔TCP port-forward** (guest :18789 → host localhost) and confirm a host client can reach a guest listener.
5. Inside the guest, run the S0.1 harness against **a real Node-based agent workload** (a small Node process is acceptable floor; a Claude Code Linux build against a projected workspace is the real target) that writes into `/mnt/host/test` and makes a network connect.
6. Probe the virtiofs seams on the projected dir: SQLite open/write (POSIX/flock locking), and whether in-guest watchers receive events for **host-side** file changes (expected: no — record it for LIMITS.md).
7. Stream decoded events over vsock to the host; print them host-side with paths translated `/mnt/host/test/... -> <realhostpath>`.

## Success criteria
- [ ] Guest boots cold in ≤ 10s (record the number; it seeds G3).
- [ ] Files written in-guest to `/mnt/host/test` are visible on the host at the translated path, with sane ownership (uid-1000 normalization works).
- [ ] The **same** S0.1 event types are captured in-guest as on native Linux.
- [ ] A real Node process runs from the data volume against the projected dir; SQLite on virtiofs works (or its failure mode is documented and the OpenClaw state dir moves to the data volume by design).
- [ ] Host client reaches a guest listener through the port-forward.
- [ ] inotify-for-host-changes behavior recorded (seeds the LIMITS.md virtiofs entry).
- [ ] Events arrive host-side over vsock; the host can write them (proving the host-writes-the-ledger integrity property, D15).
- [ ] Codesigning + `com.apple.security.virtualization` entitlement path documented (what a release build needs; what a source build self-signs).

## Deliverable
`spikes/S0.2-report.md`: boot time, virtiofs ownership findings, vsock throughput, entitlement/codesign notes, go/no-go. Seeds Phase 3.
